## 1. 引言

### 1.1 编写目的

本文档详细描述 AI 智能养老社区管理系统的技术架构、模块设计、接口设计、数据库设计等内容，为开发团队提供技术实现指导，为测试、运维团队提供系统参考，同时作为项目验收的技术依据。

### 1.2 项目背景

随着人口老龄化趋势加剧，养老服务需求日益增长。本系统利用互联网、人工智能等技术，为老年人提供一站式健康管理服务，包括健康数据记录、AI 健康咨询、体检预约、社区活动参与等功能，旨在提升养老服务质量和效率。

### 1.3 术语定义

| 术语 | 说明 |
|------|------|
| JWT | JSON Web Token，用于身份认证的令牌 |
| Access Token | 访问令牌，有效期 2 小时 |
| Refresh Token | 刷新令牌，有效期 7 天 |
| SSE | Server-Sent Events，服务器推送技术 |
| BMI | 身体质量指数 |
| BCrypt | 密码加密算法 |
| RBAC | 基于角色的访问控制 |

## 2. 系统概述

### 2.1 系统定位

AI 智能养老社区管理系统是一个面向养老服务场景的综合性服务平台，采用前后端分离架构，提供会员端和管理端两个入口。

### 2.2 核心功能

#### 会员端功能
- 用户认证：注册、登录、Token 刷新、登出、密码找回
- 短信验证：手机号注册验证、重要操作通知
- 健康管理：健康数据录入、历史记录查询、趋势分析
- 健康评测：问卷填写、AI 智能评分与建议
- AI 咨询：流式对话、会话上下文记忆
- 体检预约：套餐浏览、时段选择、预约/取消
- 社区活动：活动浏览、报名、签到
- 积分系统：积分获取与消费
- 消息通知：预约提醒、活动提醒、健康提醒
- 健康指导：AI 生成个性化健康建议
- 个人中心：个人信息管理

#### 管理端功能
- 仪表盘：数据概览与统计
- 会员管理：用户信息管理、状态控制
- 体检管理：套餐维护、预约时段批量生成、体检报告管理
- 评测管理：问卷与题目管理
- 活动管理：社区活动创建与维护
- 消息管理：消息推送管理
- 系统配置：参数配置、AI 提示词管理
- 积分规则配置：积分获取规则配置

### 2.3 系统特性

- **双 Token 认证机制**：确保用户身份安全，支持无感刷新
- **流式 AI 响应**：提供打字机效果的聊天体验
- **MySQL 行锁与原子操作**：保证预约名额、积分变更等并发场景下的数据一致性
- **积分体系**：注册赠送、活动签到、评测完成等多渠道获取，消费预约等场景
- **逻辑删除**：数据可追溯，避免物理删除风险
- **短信验证**：确保手机号真实性

## 5. 功能模块设计

### 5.1 认证授权模块

#### 模块职责
- 用户注册（含短信验证码）
- 用户登录
- Token 刷新
- 用户登出
- 密码找回（短信验证）
- 修改密码（登录状态下）
- Token 黑名单管理
- 管理员重置会员密码（详见会员管理模块）
- 授权管理：角色、权限、资源的配置与分配（RBAC）

#### 授权设计

系统采用基于角色的访问控制（RBAC），权限模型为"用户-角色-权限-资源"四层（标准 RBAC 规范，表设计见 6.3.19~6.3.24）：

- **角色**（role 表）：MEMBER 会员、ADMIN 管理员；用户通过 user_role 关联角色（user.role 为冗余字段，与关联表保持一致）
- **权限**（permission 表）：按业务域定义的权限点（如 member:health:list、admin:assessment:manage），角色通过 role_permission 授予权限
- **资源**（resource 表）：受控资源分三类——接口路径级资源（接口路径模式，如 /api/member/health/**，用于接口访问控制）、菜单资源（前端菜单项）、按钮资源（页面操作按钮）；权限通过 permission_resource 关联资源
- **访问判定流程**：用户登录 → user_role 取角色 → role_permission 取权限 → permission_resource 取资源 → 按路径匹配接口资源判定接口访问权限；菜单/按钮资源用于前端菜单与按钮的显隐控制
- **接口权限映射**：/api/member/** 接口需 MEMBER 角色权限；/api/admin/** 接口需 ADMIN 角色权限（详见 7.2 接口分类与 8.2 权限控制）

#### 核心流程

**注册流程**：
1. 用户输入手机号，请求发送验证码
2. 发送短信验证码到用户手机
3. 用户提交手机号、验证码、密码
4. 校验验证码正确性
5. 校验手机号是否已存在
6. BCrypt 加密密码
7. 创建用户账户，赠送 100 初始积分

**登录流程**：
1. 校验手机号和密码
2. 检查用户状态是否正常
3. 生成 Access Token（2 小时）和 Refresh Token（7 天），存储 Refresh Token 到数据库
4. 返回双 Token 和用户基本信息

**Token 刷新流程**：
1. 校验 Refresh Token 有效性，查询数据库确认
2. 检查 Access Token 是否在黑名单中
3. 生成新的 Access Token
4. 返回新 Token 对

**密码找回流程**：
1. 用户输入手机号，请求发送验证码
2. 发送验证码到用户手机
3. 用户提交验证码和新密码
4. 验证验证码正确后，更新密码
5. 将该用户所有已发放 Token 加入黑名单，强制重新登录

**修改密码流程**：
1. 用户输入原密码与新密码
2. 校验原密码正确性
3. 新密码复杂度校验（长度≥8，包含字母和数字）
4. BCrypt 加密更新密码
5. 将该用户所有已发放 Token 加入黑名单，强制重新登录

**登出流程**：
1. 将 Access Token 加入 Redis 黑名单
2. 将 Refresh Token 从数据库中删除，加入 Redis 黑名单

### 5.2 健康记录模块

#### 模块职责
- 健康数据录入（血压、血糖、心率、体重）
- 历史记录查询
- 健康趋势数据分析

#### 核心流程

**数据录入**：
1. 接收各项健康指标
2. 从用户信息获取身高，自动计算 BMI 指数（体重 kg / (身高 m)^2）
3. 保存健康记录
4. 触发健康指导生成（可选）

**趋势分析**：
1. 查询最近 6 个月健康数据
2. 按指标类型分组统计
3. 计算平均值、最大值、最小值
4. 返回趋势图表数据

**健康提醒触发条件**：
数据录入完成后，系统按以下阈值判断是否生成健康提醒（指标超出范围时触发）：

| 指标 | 正常范围（成人） | 触发条件 |
|------|------------------|----------|
| 收缩压 | 90-139 mmHg | <90 或 ≥140 |
| 舒张压 | 60-89 mmHg | <60 或 ≥90 |
| 空腹血糖 | 3.9-6.1 mmol/L | <3.9 或 >6.1 |
| 心率 | 60-100 次/分 | <60 或 >100 |
| BMI | 18.5-23.9 | <18.5 或 ≥24 |
| 体重 | （按 BMI 派生） | 同 BMI |

触发流程：
1. 任意指标命中触发条件，生成 `health_guidance` 记录，关联本次录入
2. 调用 AI 生成个性化健康建议（基于超标项）
3. 通过站内消息推送给用户（message 表 type=健康提醒）
4. 同一指标当日多次超标只推送一次（去重：user_id + indicator + 当天，indicator 记录于 health_guidance 表，见 6.3.13）

#### 管理端职责
- 会员健康档案查询：按会员分页查询健康记录（支撑会员详情页"健康记录"标签，对应 /api/admin/health-record）
- 会员健康趋势查询：查看某会员指定指标的近 6 个月趋势数据（与会员端趋势分析共用统计逻辑，见上方趋势分析）

### 5.3 健康评测模块

#### 模块职责
- 问卷列表查询
- 题目获取
- 评测提交
- AI 评分与建议生成
- 评测历史查询

#### 核心流程

**评分机制**：

- 题目按性质分两类（question.score_mode）：计分题——程度/频率/习惯类（如睡眠质量、运动频率、饮食口味），每个选项配置分值（options 内 text+score），参与规则分；非计分题——事实/类别/病史类（如年龄段、是否吸烟、家族史），选项仅配置文案（options 内仅 text），不参与规则分，作为 AI 评估的参考信息（避免对无好坏梯度的选项强行打分）
- 选项意义（meaning）：出题时每个选项配置标准语义文本（如"很好，每天睡 7-8 小时"→"睡眠充足，质量良好"），计分题与分值并存、非计分题仅有语义；选项意义由管理员配置确定，AI 不得另行解读，作为 AI 评分与报告解读的统一依据（标准规范可循）
- 出题配置：计分题配置选项分值；文本题配置满分 max_score（由 AI 评估）；问卷配置满分 total_score（仅计分题 max_score 之和）、及格线 pass_score（百分制）与等级规则 grade_rules
- 规则分计算：提交答卷时仅对计分题按选项分值加总（单选取所选项分值；多选取所选项分值之和、上限为该题 max_score；非计分题与文本题不计入），换算百分制 rule_score = ROUND(Σ计分题得分 / total_score × 100)
- AI 综合评分：将问卷信息、全部题目与答案（每题选项的 text+meaning、计分题规则分、非计分题答案、主观题文本）提交 AI 接口，AI 仅基于选项标准意义评定，输出百分制 ai_score 与个性化建议 ai_suggestion（ai_score 为最终展示分），并在建议中简述评定依据
- 等级判定：按 grade_rules 区间匹配 ai_score，得出优秀/良好/及格/需关注等结论，随评测报告展示
- 报告展示：评测报告逐题展示所选选项的 text、meaning 与 score（如有），使用户理解每个选项代表的意义与评分依据
- 示例："您的睡眠质量如何？"（计分题，很好 10/一般 6/较差 3/非常差 1，meaning 如"睡眠充足，质量良好"）参与规则分；"您的年龄是？""您是否吸烟？"（非计分题）不参与计分，仅由 AI 结合选项意义评估

**评测提交**：
1. 接收用户答案
2. 保存答案快照（answers JSON 含每题 score/max_score，见 6.3.7）
3. 计算规则分 rule_score（百分制）
4. 调用 AI 接口智能评分（综合规则分与主观题答案），输出 ai_score 与 ai_suggestion
5. 按 grade_rules 判定等级
6. 保存评测结果（完成评测赠送 20 积分，见 5.8 积分流水）

#### 管理端职责

- 问卷创建与编辑（CRUD，对应 questionnaire 表），配置问卷满分（total_score）、及格线（pass_score）与等级规则（grade_rules）
- 问卷题目管理（单选/多选/文本类型），区分计分模式（计分/非计分）：计分题维护选项分值（options 内 score）与题目满分（max_score），非计分题仅维护选项文案；维护排序
- 问卷发布/下架（status：草稿/已发布）

对应接口：/api/admin/assessment

### 5.4 AI 对话模块

#### 模块职责
- 会话创建
- 消息发送
- 流式响应（SSE）
- 对话历史查询
- 会话管理

#### 核心流程

**流式对话**：
1. 创建 SSE 连接
2. 获取最近 10 轮对话上下文（超过截断最早对话）
3. 调用 AI 大模型接口（流式）
4. 逐字推送到前端（打字机效果）
5. 保存用户消息和 AI 回复

> **会话管理**：
>
> 1. 会话创建：创建时 session_name 置空；发送首条用户消息后，调用 AI 根据首条消息内容生成会话名称（简短标题，如"高血压饮食咨询"）
> 2. 会话命名兜底：AI 生成名称失败或超时时，取首条消息前 20 字作为会话名称
> 3. 会话列表：按 update_time 倒序返回当前用户未删除的会话（最近对话置顶）
> 4. 删除会话：会话与所属全部消息一并逻辑删除（deleted=1），列表不再展示；物理清理按 6.9.3 保留策略执行（消息保留 6 个月，会话同步清理）

> **中断与异常处理**：
> - 客户端中途断开（SSE 连接断开）：捕获流写入异常，将已接收内容保存为完整消息（不丢失）
> - AI 接口超时（>60s）：主动断开流并保存已接收片段，提示用户重试
> - AI 接口错误：保存用户消息（role=USER），AI 消息保存为失败标记（status=FAILED，content=错误信息）
> - 所有 AI 回复均需保存到 `ai_conversation_message`，无论成功、中断或失败，保留完整对话历史

### 5.5 体检预约模块

#### 模块职责
- 套餐列表查询
- 可预约时段查询
- 预约提交
- 预约取消
- 预约记录查询
- 体检报告上传/查看

#### 核心流程

**预约提交（并发控制）**：
1. 校验用户积分是否充足
2. 校验用户状态正常（未禁用）
3. 检查时段是否还有剩余名额
4. 数据库原子扣减用户积分（`UPDATE user SET points = points - ? WHERE id = ?`），并按 FIFO 扣减获得批次、生成预约消费流水（见 5.8 积分流水）
5. 数据库原子增加时段预约人数（`UPDATE appointment_slot SET current_count = current_count + 1 WHERE id = ?`）
6. 创建预约记录
7. 发送预约成功短信通知

> **事务边界**：上述步骤 4-6 必须包裹在同一个 `@Transactional` 中，任一失败整体回滚，避免"积分已扣但预约未创建"或"名额已增但积分未扣"等异常；步骤 7（短信）需做容错（短信失败不影响主事务回滚结果，但需记录失败日志以便补发）。
> **并发安全**：步骤 4 和步骤 5 均为 MySQL 行级原子操作，单机项目无跨进程竞争，单事务内即可保证一致性。

**预约取消**：
1. 检查预约状态是否可取消（未过期且未完成）
2. 数据库原子退还用户积分（按原批次还原，见 5.8 积分流水）
3. 数据库原子减少时段预约人数
4. 更新预约状态为已取消
5. 发送取消通知短信

> **事务边界**：步骤 2-4 在同一个 `@Transactional` 内；步骤 5 容错处理。

**预约状态流转**：

| 状态 | 触发时机 | 操作方 |
|------|---------|--------|
| 待确认 | 预约提交成功 | 系统 |
| 已确认 | 管理员在管理端确认预约 | 管理员 |
| 已完成 | 管理员上传体检报告时自动置为已完成 | 管理员 |
| 已取消 | 用户取消（未完成且未过期）；管理员也可取消 | 用户/管理员 |

**体检报告流程**：
1. 体检完成后，管理员在管理端选择预约记录并上传报告 PDF 文件
2. 后端将文件存储到 `data/upload/report/yyyyMM/{uuid}.pdf`（按年月分目录），文件大小上限 20MB，仅允许 PDF 格式
3. 文件路径写入 `appointment.report_url`（相对路径），同时记录原始文件名（original_filename）、上传时间（report_upload_time）、上传管理员（upload_admin_id）
4. 用户在会员端"我的预约"详情页查看报告，后端做权限校验：仅预约本人或管理员可访问
5. 报告下载由后端代理（不直链磁盘路径），URL 含短期签名（5 分钟有效），防止盗链

> **存储说明**：单机项目下文件存储于本地磁盘，由 Spring Boot 静态资源目录或专用下载接口提供访问；如未来需扩展为对象存储（OSS/MinIO），可在 `FileStorageService` 接口下扩展实现，业务代码无需改动。

#### 管理端职责

- 体检套餐增删改查（appointment_package）
- 批量生成预约时段（appointment_slot，按套餐/日期批量生成）

### 5.8 积分管理模块

#### 积分获取规则
- 新用户注册：+100 积分
- 活动签到：+50 积分
- 完成健康评测：+20 积分
- 邀请好友（可选扩展）：+100 积分

> 每笔获得积分生成一条 point_transaction 获得类流水（见 6.3.18），expire_time = 获得时间 + 1 年。

#### 积分消费规则
- 体检预约：根据套餐价格扣除相应积分
- 积分兑换礼品（可选扩展）：扣除对应积分

> 消费时按 FIFO 优先扣减最早获得的积分批次（remain_amount），按批次生成消费流水并同步原子扣减 user.points（见下方积分流水）。

#### 积分过期策略
- 积分获得后 1 年有效，到期自动清除过期积分
- 实现机制：每日定时任务扫描 point_transaction 中 remain_amount > 0 且 expire_time < NOW() 的积分批次，按批次生成过期扣减流水并同步原子扣减 user.points
- 过期清理与余额对账均以积分流水表为依据（见 6.3.18）
- 积分过期清理定时任务见 5.12 定时任务列表（系统级）

#### 积分流水

积分流水表 point_transaction（见 6.3.18）记录每一笔积分变动，是积分余额、FIFO 消费与过期清理的唯一依据：

- **获得**：注册赠送、活动签到、评测完成、管理员调增，生成获得类流水（remain_amount = change_amount，expire_time = 获得时间 + 1 年）
- **消费**：体检预约、管理员调减，按 FIFO 优先扣减最早获得的批次，每个被扣批次生成一条消费流水（batch_tx_id 指向该批次），并同步原子扣减 user.points
- **取消退还**：预约取消时按原批次还原——对应消费流水逻辑删除（deleted=1），批次 remain_amount 加回，原有效期继续有效（不重新起算，防止反复预约-取消无限续期）
- **过期清理**：每日定时任务将已过期且未消费的批次生成过期流水，批次 remain_amount 置 0，user.points 同步扣减
- **对账**：user.points = 获得流水 change_amount 之和 - 未删除消费流水 change_amount 绝对值之和

各模块产生的定时任务统一在此汇总管理，任务触发逻辑详见对应模块：

| 任务 | Cron | 实现 | 说明 | 所属模块 |
|------|------|------|------|------|

## 6. 数据库设计

### 6.1 数据库设计概述

#### 6.1.1 设计目标

本数据库设计旨在为 AI 智能养老社区管理系统提供稳定、高效、可扩展的数据存储方案，支持用户管理、健康记录、体检预约、社区活动、AI 对话等核心业务功能。

#### 6.1.2 设计原则

- **规范性**：遵循数据库三大范式，减少数据冗余
- **性能优先**：合理设计索引，优化查询性能
- **可扩展性**：预留扩展字段，支持业务迭代
- **安全性**：逻辑删除替代物理删除，数据可追溯
- **易用性**：命名规范统一，字段含义清晰

#### 6.1.3 数据库基本信息

| 项目 | 说明 |
|------|------|
| 数据库类型 | MySQL 9.7.2 |
| 字符集 | utf8mb4 |
| 排序规则 | utf8mb4_0900_ai_ci |
| 存储引擎 | InnoDB |
| 数据表数量 | 24 |
| 初始数据库大小 | 约 50 MB |

#### 6.1.4 命名规范

##### 表命名规范
- 使用小写字母和下划线
- 采用名词单数形式
- 前缀：业务模块名 + 下划线 + 表名
- 示例：`user`, `health_record`, `appointment_package`

##### 字段命名规范
- 使用小写字母和下划线
- 主键统一命名：`id`
- 外键命名：关联表名 + 下划线 + id
- 布尔类型：`is_` 前缀
- 时间类型：`_time` 后缀；日期类型：`_date` 后缀
- 状态类型：`status`
- 示例：`user_id`, `create_time`, `is_read`, `member_level`

##### 索引命名规范
- 主键索引：`PRIMARY`（系统默认）
- 唯一索引：`uk_` + 字段名
- 普通索引：`idx_` + 字段名
- 组合索引：`idx_` + 字段名1 + 下划线 + 字段名2

### 6.2 数据库环境配置

#### 6.2.1 创建数据库

```sql
CREATE DATABASE IF NOT EXISTS eldercare

COLLATE utf8mb4_0900_ai_ci;

USE eldercare;
```

#### 6.2.2 字符集说明

使用 `utf8mb4` 字符集原因：
- 完整支持 Unicode 字符，包括 emoji 表情
- 兼容 utf8，是 utf8 的超集
- 支持生僻字、特殊符号等

#### 6.2.3 存储引擎选择

使用 InnoDB 存储引擎：
- 支持事务，保证数据一致性
- 支持行级锁，并发性能好
- 支持外键约束，数据完整性有保障
- 支持崩溃恢复，数据安全性高

**answers 字段 JSON Schema**：

```json
{
  "version": 1,
  "items": [
    {"qid": 1, "type": "单选",   "value": 2,   "score": 8,   "max_score": 10},
    {"qid": 2, "type": "多选", "value": [0, 3], "score": 12,  "max_score": 20},
    {"qid": 3, "type": "文本",     "value": "睡眠质量一般，半夜易醒", "score": 6, "max_score": 10}
  ]
}
```

- `version`：快照格式版本号，便于以后 schema 演进
- `items`：有序数组，按题目顺序保存
  - `qid`：题目 ID（对应 question.id）
  - `type`：题目类型，与 question.type 一致
  - `value`：
    - 单选：存选项下标（数字）
    - 多选：存选项下标数组（数字数组）
    - 文本：存字符串
  - `score`：该题得分（仅计分题有值，为选中选项分值之和、上限为该题 max_score；非计分题与文本题无此项）
  - `max_score`：该题满分（与 question.max_score 一致，非计分题为 0）

#### 6.3.18 积分流水表（point_transaction）

**表说明**：存储用户积分的每一笔变动流水，是积分余额、FIFO 消费与"积分 1 年有效期"过期清理的唯一依据，支撑 4.3.1 积分规则与 4.1.8 积分明细查看

| 字段名 | 数据类型 | 约束 | 默认值 | 说明 |
|--------|---------|------|--------|------|
| id | BIGINT | PRIMARY KEY AUTO_INCREMENT | - | 流水 ID |
| user_id | BIGINT | NOT NULL | - | 用户 ID |
| type | VARCHAR(20) | NOT NULL | - | 类型：注册赠送/活动签到/评测完成/体检预约/管理员调整/积分过期 |
| change_amount | INT | NOT NULL | - | 变动积分（正=获得，负=扣减） |
| balance_after | INT | NOT NULL | - | 变动后积分余额 |
| remain_amount | INT | NOT NULL | 0 | 获得类流水的剩余可用积分，消费按 FIFO 扣减；消耗类流水为 0 |
| expire_time | DATETIME | NULL | NULL | 获得类流水的过期时间（获得时间 + 1 年）；消耗类流水为空 |
| batch_tx_id | BIGINT | NULL | NULL | 消耗类流水关联的被扣获得批次流水 ID（按批次拆分时每条对应一个批次） |
| description | VARCHAR(200) | NULL | NULL | 业务说明 |
| ref_id | BIGINT | NULL | NULL | 关联业务记录 ID（如预约 ID、报名 ID、评测 ID） |
| create_time | DATETIME | NULL | CURRENT_TIMESTAMP | 创建时间 |
| update_time | DATETIME | NULL | CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP | 更新时间 |
| deleted | TINYINT | NULL | 0 | 逻辑删除（取消退还时消费流水标记 deleted=1） |

**索引设计**：
- PRIMARY KEY (`id`)
- KEY `idx_user_id` (`user_id`)
- KEY `idx_expire_remain` (`expire_time`, `remain_amount`)

> **积分批次与有效期规则**：获得类流水（注册赠送/活动签到/评测完成/管理员调增 正值）记录 remain_amount（剩余可用）与 expire_time（获得时间 + 1 年）；消费时按 FIFO 优先扣减最早获得的批次，每个被扣批次生成一条消费流水（batch_tx_id 指向该批次）；取消预约退还将对应消费流水逻辑删除（deleted=1）并把批次 remain_amount 加回，原有效期继续有效（不重新起算，防止反复预约-取消无限续期）；过期清理任务每日扫描 remain_amount > 0 且 expire_time < NOW() 的批次，生成 EXPIRE 流水并同步扣减 user.points。对账口径：user.points = 获得流水 change_amount 之和 - 未删除消费流水 change_amount 绝对值之和。

### 6.5 索引设计

#### 6.5.1 索引设计原则

1. **主键索引**：所有表必须有主键，使用自增 BIGINT
2. **外键索引**：所有关联字段必须建立索引
3. **查询字段**：经常作为 WHERE 条件的字段建立索引
4. **排序字段**：经常用于 ORDER BY 的字段建立索引
5. **组合索引**：遵循最左前缀原则，区分度高的字段放前面

#### 6.5.3 索引使用注意事项

1. **避免索引失效**：
   - 不在索引列上使用函数或运算
   - 避免 LIKE 以 `%` 开头
   - 避免使用 NOT、!=、<> 操作符
   - 组合索引遵循最左前缀原则

2. **索引维护**：
   - 定期检查慢查询日志，识别需要优化的查询
   - 定期分析索引使用情况，删除冗余索引
   - 数据量大的表，新增索引考虑在业务低峰期执行

#### 6.9.5 常见问题处理

##### 问题 1：数据库连接耗尽
- 检查连接池配置（最大连接数、最小空闲连接）
- 排查未释放连接的代码（特别是异常分支）
- 优化慢查询，减少连接占用时间
- 必要时上调连接池上限，但需同步上调 MySQL 的 max_connections

##### 问题 2：死锁

## 8. 安全设计

### 8.1 认证安全

#### JWT 双 Token 机制
- **Access Token**：有效期 2 小时，用于 API 访问
- **Refresh Token**：有效期 7 天，用于刷新 Access Token，持久化存储在数据库
- 支持用户主动注销所有设备登录（删除所有 Refresh Token）

#### 黑名单机制
- 登出时将 Access Token 加入 Redis 黑名单
- 黑名单设置与 Token 有效期一致的过期时间
- 每次请求校验 Token 是否在黑名单中
- **Key 命名规范**：
  - 单 Token：`jwt:blacklist:{jti}`，value 为 1，TTL 与 Token 剩余有效期一致
  - 用户级（强制下线所有设备）：`jwt:blacklist:user:{userId}`，TTL 同 Refresh Token
  - `jti`（JWT ID）作为 Token 唯一标识，需在签发 Token 时生成并写入 payload

#### 密码安全
- 使用 BCrypt 算法加密存储密码
- BCrypt 自带盐值，防彩虹表攻击
- 注册时强制密码复杂度校验（长度≥8，包含字母和数字）

### 8.2 权限控制

基于 RBAC 四层权限模型（用户-角色-权限-资源，见 5.1 授权设计与 6.3.19~6.3.24）：

- **角色**：MEMBER 会员、ADMIN 管理员（role 表，用户经 user_role 关联，user.role 为冗余字段）
- **权限**：按业务域定义的权限点（permission 表，经 role_permission 授予角色）
- **资源**：接口路径资源、菜单资源、按钮资源（resource 表，经 permission_resource 关联权限）

接口访问控制：
- 路径级：`/api/member/**` 接口需 MEMBER 相关权限；`/api/admin/**` 接口需 ADMIN 相关权限
- 方法级：`@PreAuthorize` 注解校验权限编码（如 admin:assessment:manage）
- 资源级：数据归属校验（如体检报告仅预约本人或管理员可访问，见 5.5）

实现方式：
- Spring Security 配置路径权限
- 自定义`JwtAuthenticationFilter`进行 Token 校验，解析角色与权限集
- 角色-权限-资源映射缓存至 Redis（变更时刷新）
- JWT 无状态架构禁用 CSRF 防护

前端控制：
- 菜单/按钮资源按当前用户权限渲染（管理端菜单项、发布问卷/上传报告等按钮显隐）

### 8.3 数据安全

#### 逻辑删除
- 所有业务表使用逻辑删除（deleted 字段）
- MyBatis 框架下，统一在 Mapper XML / 注解 SQL 中手动拼接 `AND deleted = 0` 过滤已删除数据
- 数据可追溯，支持恢复

#### SQL 注入防护
- 使用 MyBatis #{} 参数化查询
- 禁止 SQL 字符串拼接

#### XSS 防护
- 前端输入转义
- 后端输出编码

#### 敏感数据加密
- 用户健康数据等敏感信息对关键字段进行加密存储
- 采用 AES-256 对称加密算法，密钥通过环境变量管理，不写入配置文件
- 需要加密的关键字段：健康记录中的备注（memo）等自由文本字段
- 血压、血糖等数值指标需支持趋势聚合、阈值判断与范围查询（见 5.2、6.3.4），以明文结构化存储，通过 HTTPS 传输加密与 RBAC 访问控制保护
- 密码已经 BCrypt 加密，无需额外处理

### 8.4 接口安全

#### 跨域配置
- 配置 CorsConfig 允许指定域名访问
- 支持预检请求（OPTIONS）
- 配置允许的请求头和方法

#### 请求限流
- 基于 Redis + Lua 实现接口限流（滑动窗口算法）
- 对登录、注册、短信接口进行限流，防止恶意攻击
- 默认配置：登录接口 6 次/分钟（按 IP 限流），短信接口 3 次/分钟（按手机号限流）
- 额外限制：同一手机号一天最多发送 10 条验证码，防止短信轰炸

**限流维度**：

| 接口 | 维度 | 限流规则 | Key 命名规范 |
|------|------|----------|--------------|
| 发送短信验证码 | 手机号 | 3 次/分钟 | `rl:sms:{phone}` |
| 发送短信验证码 | 手机号 | 10 次/天 | `rl:sms:day:{phone}:{yyyyMMdd}` |
| 登录 | IP | 6 次/分钟 | `rl:login:ip:{ip}` |
| 登录 | 手机号+密码错误 | 5 次锁定 30 分钟 | `rl:login:err:{phone}` |
| 注册 | IP | 5 次/小时 | `rl:register:ip:{ip}` |
| 通用 API | 用户 ID | 60 次/分钟 | `rl:api:user:{userId}` |

限流命中返回统一错误码 `429 TOO_MANY_REQUESTS`，响应头 `Retry-After` 告知剩余冷却秒数。

### 8.5 生产环境强制要求
- 必须使用 HTTPS，配置 SSL 证书
- 禁止对外开放数据库、Redis 直接访问
- 所有敏感配置使用环境变量或配置中心管理，禁止提交到代码仓库

## 9. 性能设计

### 9.1 缓存策略

#### Redis 缓存应用场景
1. **Token 黑名单**：快速判断 Token 有效性
2. **热点数据缓存**：系统配置、热门套餐、活动列表
3. **短信验证码缓存**

### 9.2 数据库优化

#### 索引设计
- 外键关联字段建立索引
- 常用查询条件建立组合索引
- 唯一约束字段建立唯一索引
- 避免过度索引，索引数量建议单表不超过 5 个

#### 查询优化
- 使用 PageHelper 实现分页（基于 MyBatis 拦截器）
- 避免 SELECT *，按需查询字段
- 大表查询限制返回条数
- 事务隔离级别：读已提交（Read Committed），对于高并发场景避免可重复读

### 9.3 并发控制

项目为单机部署，应用层不引入分布式锁，并发控制由 MySQL 行锁与事务隔离保证。

#### 数据库行锁
- 体检预约名额扣减：`UPDATE appointment_slot SET current_count = current_count + 1 WHERE id = ? AND current_count < max_count`，利用行锁保证并发安全
- 活动报名名额控制：`UPDATE community_activity SET current_participants = current_participants + 1 WHERE id = ? AND current_participants < max_participants`
- 同一记录同一时刻只有一个事务能更新成功，更新失败的请求直接拒绝

#### 原子操作
- 积分变更：使用数据库原子加减 `UPDATE user SET points = points + ? WHERE id = ?`
- 预约人数：使用数据库原子加减
- 事务保证一致性，避免数据异常

### 9.4 连接池配置
- 使用 HikariCP 连接池（Spring Boot 默认）
- 建议最大连接数设置：CPU 核心数 * 2 + 1
- 根据实际负载调整参数

### 13.2 核心测试要点

#### 13.2.1 并发场景测试
- **预约扣减测试**：模拟多个用户同时预约同一个时段，验证不会超卖

- **积分并发测试**：模拟多个请求同时增加/扣减积分，验证积分正确性
- **行锁与事务测试**：验证 MySQL 行锁在并发场景下保证数据一致性（如预约名额扣减、积分变更不出现负数或超扣）

#### 13.2.2 安全测试要点
- 验证未携带 Token 请求被拒绝
- 验证普通用户 Token 无法访问管理端接口
- 验证 SQL 注入防护（参数化查询生效）
- 验证 Token 黑名单机制：登出后 Token 无法继续使用
- 验证短信接口限流：超过频率限制后被拒绝

#### 13.2.3 边界条件测试
- 积分刚好足够预约 / 积分差 1 分无法预约
- 最后一个名额被预约后，后续请求失败
- 验证码过期后无法使用
- Refresh Token 过期后无法刷新
- 软删除数据无法被查询到
